## git flow
### Branching strategy
The `main` branch is used for hosting the live website. We do not work directly in this branch.

We work in a separate branch called `dev`. When you are building something, you create a new branch from the `dev` branch. Once the feature is finished, you can open a pull request. After it has been approved by the team, the branch may be merged into the `dev` branch.

After a branch has been merged, it should be archived to keep an overview of the active branches.  
[Here](https://docs.fdnd.nl/conventies.html#archiving-branches) you can find instructions on how to do this, including an example of archiving branches:
<img width="952" height="256" alt="Image" src="https://github.com/user-attachments/assets/062cb3bc-264f-4594-b2f3-bebbebd59e38" />

Branch names are generated by GitHub.  
Within an issue, you can create a branch on the right-hand side:

## Assigned Issues
### Current workflow (from sprint 17 onward)
Starting from sprint 17, we adjusted our workflow. At the beginning of each sprint, all issues that need to be addressed during the sprint are placed in the **To Do** column. Team members pick up the next available issue and only start a new one once the previous issue has been completed.

### Past workflow (before sprint 17)
Issues were first discussed before being assigned. This ensured that the workload was distributed fairly and that no one only picked the easiest issues.


## Definition of Ready
- The user story is written as: `As ... I would like ... so that ...`
- Weigh user stories
- Create sub-issues to split each user story into tasks
- A task (or sub-issue) should include everything that belongs to it. For example, fetching data and rendering it in the HTML should be part of the same task
- Prioritize the user stories using the MoSCoW method


## Definition of Done
- **Testing**
    - HTML validator test
    - Browser testing
    - Lighthouse test
    - Device testing
    - User testing
    - Responsiveness checks
    - Accessibility testing ([a11y checklist](https://www.a11yproject.com/checklist/))
- **Code**
    - FDND conventions are followed
    - Remove commented-out code
    - Prevent repeated code (DRY principle)
- **Pull requests**
    - Close sub-issues when finished
    - Move the user story to the review column
    - Write a detailed pull request and ask for feedback on specific parts
        - Include all information needed for the review in the pull request
    - Verify that you are merging into the correct branch (`dev`)
    - Archive closed branches
